# СБП во внешнем кабинете

## Фоновая сверка без открытого кабинета

`sbp-worker` в Compose использует образ API, не публикует порты и по умолчанию
бездействует: `PUSHOK_SBP_RECONCILIATION_ENABLED=0`. После отдельной приёмки значение
`1` разрешает проверку уже созданных счетов. Флаг выставления новых счетов независим:
его отключение не останавливает сверку старых. Примените миграцию
`017_sbp_background.sql` перед запуском обновлённых API/worker; `setup.sh` включает её.

Проверка выполняется раз в минуту пакетами по 20 счетов. Только авторитетный GET
провайдера может подтвердить оплату. Сохраняются ограничения владельца магазина,
test/live, идентификатора, суммы, валюты и статуса кампании. Сверяется конкретный
сохранённый attempt, а не последний счёт кампании. Сетевые ошибки повторяются
с задержкой до часа; спорные ответы переводятся в `sbp_requires_review`, без зачёта.
Состояние «created» без ID провайдера требует отдельного разбора и не закупается
повторно worker. Никаких новых POST к банку или активации спонсора.

На тестовом стенде просмотр без сети/изменения платежей:
`docker compose exec -T sbp-worker python -m app.sbp_worker --once`.
Один применяющий пакет при включённом серверном флаге:
`docker compose exec -T sbp-worker python -m app.sbp_worker --once --apply`.
Одновременно работает один worker (session advisory lock); пользовательская
сверка сериализуется блокировкой кампании. После аварии сохраняется повторная
проверка. Журнал службы содержит только счётчики, без секретов и ответов банка.

Администратор видит разрешение фоновой сверки, число ожидающих счетов и число
спорных попыток в «Настройки → Платежи». Разрешение в конфигурации не доказывает
живую работу процесса. Диагностика: `docker compose ps sbp-worker` и
`docker compose logs --tail=20 sbp-worker`. Спорную попытку сначала сверить с банком
по сохранённому ID и проверить магазин/режим/сумму. Только после устранения причины
администратор может открыть очередь СБП в «Настройки → Платежи» и отправить
конкретную попытку на повтор с комментарием. Не изменять `status` или сумму вручную.

### Очередь и повтор из кабинета

Миграция `019_sbp_review_revision.sql` применяется установщиком перед обновлением.
API администратора: `GET /api/v1/admin/payments/sbp/attempts?offset=0&limit=50`
(до 100 записей на страницу) и `POST /api/v1/admin/payments/sbp/attempts/{id}/retry`
с телом `{"revision":0,"note":"Проверены настройки магазина"}`. Доступ только admin;
рекламодатель и оператор получают отказ. Ответ списка приватный, без ключей,
платёжных ссылок и исходных ответов банка.

Список содержит ожидающие и неизвестные результаты создания, тестовый/боевой режим,
сумму, ID попытки/кампании/провайдера, задержку и диагностическую категорию. Категория
«ответ не прошёл проверку» не подменяет подробную сверку у эквайера. Завершённые
платежи остаются в отчётах кампании, а не в очереди.

Повтор требует работающей конфигурации фоновой сверки, совпадения магазина/режима,
сохранённого ID провайдера, статуса pending и актуальной revision. Обязателен
комментарий 12–300 символов без секретов. Запрос атомарно записывает администратора,
причину и ID попытки в audit_events, сбрасывает задержку/флаг ручного разбора и
ставит GET-сверку на ближайший проход worker. Ответ queued НЕ подтверждает оплату.
Устаревшая форма и повтор того же запроса получают 409; обновите список.
Worker использует revision, чтобы запоздалый результат старой проверки не затёр
новый запрос администратора. При остановленном процессе очередь сохранится до
возобновления службы; разрешение флагом не доказывает живую работу worker.

Попытки created без ID провайдера не отправляются повторно в банк и не получают
кнопку повторного создания: сначала нужен отдельный разбор неизвестного результата.
Ручного зачёта, изменения цены, снятия проверки магазина или запуска спонсора здесь нет.

Webhook дополняет фоновые проверки (см. ниже). Живой эквайринг, нагрузка и VPS
требуют отдельной приёмки.

Код связывает кабинет с серверным клиентом ЮKassa. До отдельной приёмки новые
счета выключены: `PUSHOK_SBP_PAYMENTS_ENABLED=0`. Факт наличия кода и успешные
тесты не подтверждают настоящий банковский платёж.

## Настройка отдельного стенда

### Уведомления ЮKassa

После миграции `018_sbp_webhook.sql` endpoint:
`POST https://<домен-кабинета>/api/v1/payments/sbp/webhook`.
Подпишите тестовый магазин на `payment.succeeded` и `payment.canceled` по
[официальной инструкции](https://yookassa.ru/developers/using-api/webhooks).
Не добавляйте ключ магазина или секрет в URL. Значения сохраняются только на сервере:

```dotenv
PUSHOK_SBP_WEBHOOK_ENABLED=0
PUSHOK_SBP_RECONCILIATION_ENABLED=0
```

На отдельном стенде после проверки конфигурации разрешите оба флага и перезапустите
API и worker. На рабочем сервере автоматически ничего не включается. Если endpoint
выключен, он отвечает 404; если приём разрешён, но фоновая сверка запрещена — 503.
Отсутствие/остановка самого процесса worker определяется через Compose/logs,
а не только по флагу. Периодическая сверка остаётся резервом при потере уведомления.

Endpoint публичный: тело callback считается недоверенным и НЕ является доказательством
платежа. Используются только тип события и ID, совпавший с сохранённым ожидающим
СБП-счётом. Сумма, metadata, paid и status из callback не меняют кампанию. Первый
сигнал атомарно сохраняется в БД и приближает очередной GET (обычно до следующего
минутного прохода worker); повторы не сбрасывают backoff и ручную сверку.
Даже поддельное уведомление о существующем ID не может подтвердить оплату:
проверка суммы, магазина, валюты и test/live выполняется по серверному GET.

HTTP 200 означает только принятие сигнала. Неизвестный ID, уже завершённая попытка
и повтор получают тот же пустой ответ; информация о счёте не раскрывается.
При сбое БД возвращается 503 для повторной доставки. Не относящиеся к платежам
события подтверждаются без изменений; возвраты автоматически не обрабатываются.
Неверный JSON/формат — 400, иной Content-Type — 415, тело больше 16 KiB — 413,
независимо от заявленного Content-Length. Тело callback и ключи не журналируются.
На reverse proxy настройте ограничение размера и частоты запросов; проверку IP
провайдера можно добавить по его актуальной документации, без доверия произвольному
X-Forwarded-For. Реальная доставка webhook требует отдельной приёмки у провайдера.

Переменные хранятся только на сервере в `.env` с правами 0600:

```dotenv
PUSHOK_SBP_PAYMENTS_ENABLED=0
PUSHOK_SBP_TEST_MODE=1
PUSHOK_PUBLIC_PAYMENT_HOST=ads.example.org
YOOKASSA_SHOP_ID=
YOOKASSA_SECRET_KEY=
```

Замените домен своим HTTPS-доменом кабинета, без протокола, пути и порта.
Магазин и ключ берутся в кабинете эквайера. Не отправляйте их в чат, Git или
формы веб-кабинета. Включение новых счетов выполняется на сервере только после
проверки настроек и готовности выбранного магазина к СБП. Значение режима
`1` требует `test=true` в объекте провайдера, `0` — `test=false`. Это проверка
ответа эквайера, а не способ превратить реальные ключи в тестовые. Совместимость
тестового магазина со способом СБП проверяется отдельно. Несовпадение режима
блокирует выдачу ссылки и подтверждение оплаты.

`setup.sh` применяет миграцию `016_sbp_web_checkout.sql` для существующей базы.
Перед обновлением нужна резервная копия. Для чистой базы миграцию применяет
PostgreSQL при инициализации. В Compose API получает сеть `payment-egress` для
исходящего HTTPS; база остаётся во внутренней сети. Внешние обращения к API
по-прежнему идут через настроенный reverse proxy.

## Сценарий

1. Рекламодатель открывает «Оплата» → свою одобренную заявку.
2. Если сервер разрешил СБП, кнопка «Выставить счёт» создаёт или возвращает
   уже открытую попытку. Сумма берётся из снимка цены заявки, не из браузера.
3. Сервер сохраняет ключ запроса отдельной транзакцией **до** запроса эквайринга.
   Тайм-аут оставляет состояние `created`; повтор использует тот же ключ и
   сохранённые сумму/return URL. Другой одновременно открытый платёж блокируется.
4. После ответа эквайринга кабинет показывает HTTPS-ссылку «Перейти к оплате».
   Переход идёт в той же вкладке, чтобы сохранить сессию при возвращении.
5. Возврат с `?sbp_campaign=UUID` не является подтверждением. Кабинет проверяет
   наличие собственной попытки и вызывает серверную сверку. Если сессия истекла,
   сначала требуется повторный Telegram-вход.
6. Сервер запрашивает текущий объект платежа у эквайера и проверяет ID, канал
   СБП, метаданные кампании, сумму, RUB, режим тестирования, окончательный статус,
   `paid`, захват и отсутствие возврата. Только затем атомарно подтверждает оплату.
7. Если оплата ещё не завершена, можно нажать «Проверить платёж СБП». При
   недоступности провайдера или расхождении не следует платить повторно.
8. Подтверждённая провайдером отмена позволяет выставить новую попытку.
   Повторное подтверждение успешного платежа не дублирует оплату или аудит.

Пока открыт СБП-счёт, нельзя загрузить ручной чек или выставить новый Stars-счёт
для той же кампании. Истёкший Stars-счёт без одобренного pre-checkout может быть
закрыт перед СБП. Смена магазина или режима требует разбора существующего счёта.
Смена домена блокирует повтор выпуска или продолжение старого счёта; сверка
известного ID остаётся возможной при прежнем магазине и режиме.

ЮKassa гарантирует идемпотентность 24 часа. Неопределённый выпуск старше 23 часов
блокируется до ручной сверки: новый запрос не должен создавать второе списание.

## API

Все маршруты требуют обычной Bearer-сессии и проверяют владельца кампании:

| Метод | Маршрут `/api/v1` | Назначение |
| --- | --- | --- |
| GET | `/campaigns/{id}/sbp` | Сохранённое состояние и доступность; без запроса к эквайеру |
| POST | `/campaigns/{id}/sbp/checkout` | Выпуск/повтор выпуска со снимком цены и устойчивым ключом |
| POST | `/campaigns/{id}/sbp/reconcile` | Сверка через серверный GET эквайринга |

Сумма, merchant credentials, provider ID и return URL не принимаются из тела
клиентского запроса. Ответы приватные, `no-store`. Выключение новых счетов не
мешает сверке ранее выставленного платежа при сохранённых настройках магазина.

## Границы этапа и проверка

Webhook, фоновая сверка при закрытом кабинете, автоматические возвраты и
автоматическое переключение спонсорского тега этим этапом не реализованы.
Оплата не запускает размещение. Боевой запуск требует проверки эквайринга,
чеков/настроек магазина, HTTPS и настоящего сквозного сценария на стенде.

Проверки: тесты прав и выключенного режима; реальная временная PostgreSQL для
тайм-аутов, повторов, параллельных запросов, конфликтов методов, чужих кампаний,
режима test/live, неверной суммы, возврата, отмены и повторной доставки. Браузерный
сценарий использует настоящий FastAPI/SQL, подменяя только транспорт эквайера.
До успешного CI эти проверки считаются подготовленными, а не пройденными.
