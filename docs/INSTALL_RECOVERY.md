# Повторный запуск установщика и восстановление после ошибки

Мастер остаётся интерактивным: `sudo bash setup.sh`, предварительный просмотр — `bash setup.sh --plan`. Новых обязательных вопросов не добавлено. План и отмена не создают `.env`, backup или блокировку.

## Что изменено в пакете 11–20

1. Неизвестные параметры отклоняются до диалога; выбранный порт API ограничен 1024–65535.
2. Одновременно в каталоге работает один мастер: `flock` блокирует каталог без файла с секретами. Второй запуск завершается до установки пакетов. После завершения процесса блокировка освобождается.
3. `.env` создаётся целиком с правами 0600, синхронизацией на диск и без перезаписи существующего файла. Символьная ссылка не принимается.
4. Существующая конфигурация проверяется перед изменением пакетов/сервисов. Неверные настройки сначала исправляются; секреты не печатаются.
5. Изменение реквизитов атомарно сохраняет остальные параметры и проверяет base64/UTF-8, одну строку и длину до 4000 символов.
6. Telegram можно отложить: пустые токен и username допустимы только при выключенных Mini App, Stars и тестовой среде. Некорректный непустой токен это разрешение не обходит.
7. Перед запуском БД проверяется итоговый Compose. Мастер использует те же явные файлы проекта и `.env`, что и preflight; `COMPOSE_FILE` и параметры приложения из shell не подменяют настройки.
8. Перед миграциями создаётся приватная копия PostgreSQL в `.backups/` (каталог 0700, файл 0600). Проверяются код `pg_dump`, заголовок архива и его список через `pg_restore --list`. При сбое незавершённый файл удаляется, прежние копии сохраняются; миграции не запускаются.
9. Миграции 002+ выполняются одной транзакцией psql. SQL-ошибка отменяет изменения этой транзакции; неполный или переставленный список файлов отклоняется. Ожидание блокировки ограничено 10 секундами, одного SQL-оператора — 60 секундами.
10. Готовность API требует ответа `status=ready` и `database=ok`, а не просто HTTP 200. Проверяется только localhost, без HTTP proxy/редиректов; есть таймауты и сообщение об этапе остановки. Живые Telegram, платежи и спонсор не объявляются проверенными.

## Если мастер остановился

| Этап | Действия |
|---|---|
| Блокировка | Дождаться другого запуска в том же каталоге. Не запускать вторую копию мастера из другого каталога для того же Compose-проекта |
| Проверка конфигурации | Под владельцем `.env` запустить `bash scripts/staging_preflight.sh --config-only`; при намеренно отложенном Telegram добавить `--allow-telegram-deferred` |
| Пакеты/Docker | Проверить доступность репозиториев, свободное место и Docker Compose plugin. Прерванная установка пакетов не откатывается мастером |
| PostgreSQL | Проверить состояние `docker compose ps db`. На новой установке Docker инициализирует SQL-файлы отдельно; транзакция мастера не исправляет повреждённую первоначальную инициализацию |
| Резервная копия | Проверить свободное место, владельца/права `.backups` и доступ PostgreSQL. Существующие архивы не удалять автоматически |
| Миграции | Исправить причину SQL-ошибки на отдельном стенде, затем повторить мастер. При таймауте/обрыве связи сначала проверить состояние БД: окончание клиентского процесса не доказывает прекращение серверного запроса |
| Назначение владельца/запуск сервисов | Настройки и завершённые миграции сохраняются. Повторить мастер с сохранением `.env` после исправления причины |
| API | Проверить `docker compose ps`, порт, состояние API и БД. Не считать ответ другого сервиса на том же порту успешной проверкой |

Повторный запуск: выбрать **«Сохранить настройки и обновить сервисы»**. Для бота из сохранённых данных — **«Запустить Telegram-бота из сохранённых настроек»**. Мастер не удаляет тома, не сбрасывает пароль БД и не выполняет автоматическое восстановление поверх текущей базы.

Если Telegram отложен:

```bash
bash scripts/staging_preflight.sh --allow-telegram-deferred
```

Без этого флага самостоятельный preflight по-прежнему требует настроенный Telegram. Флаг не включает бот или платежи; JSON `telegram_verified` остаётся `false`.

## Что находится в копии

`pre-migration-*.dump` содержит PostgreSQL на момент `pg_dump`. Это приватные данные, а не файл для публикации в GitHub или отправки в чат. `.backups/` и временные файлы записи `.env` исключены из Git и контекста Docker-сборки.

Копия **не включает** том чеков/скриншотов, `.env`, Caddyfile и настройки внешнего прокси. Она не является согласованным снимком всей установки при работающих сервисах. Для полного восстановления отдельно сохранить эти компоненты и проверить restore на новой пустой БД и отдельном томе по [STAGING.md](STAGING.md).

Автоматической ротации архивов и автоматического отката БД нет. После проверенного резервного копирования на другой носитель оператор определяет срок хранения и контролирует свободное место. `pg_restore --list` подтверждает читаемость структуры архива; только реальный restore подтверждает восстановление данных.

## Автоматическая приёмка

CI запускает отдельный Compose-проект со случайным именем, искусственными секретами и без опубликованных портов. Он сохраняет dump, восстанавливает его в новую тестовую БД, сверяет данные, повторяет миграции и вызывает SQL-ошибку, проверяя откат созданной таблицы. В конце удаляются только его временные контейнеры и тома.

Это подтверждение конкретного тестового сценария. Чистая установка пакетов/HTTPS на вашем Ubuntu 24.04, восстановление реальной копии, Telegram и эквайринг остаются внешними этапами приёмки.
