# MTProxy Pushok — дорожная карта пошаговой разработки

**Составлено:** 2026-11-07  
**Текущая версия кода:** v0.029 (234 Python-теста, Compose smoke, Chromium и Rust build со staging-marker rollback прошли; VPS не развёрнут); GitHub PR #15.  
**Принцип:** согласованный пакет функций → тесты → проверка → запись версии → синхронизация GitHub/GitLab. Никаких заявлений о готовности без проверки.

## Задача продукта

Создать удобную платформу монетизации MTProxy с фирменным брендом «Пушок»: Telegram-бот, мобильный веб-кабинет, административная панель, прокси-узлы и рекламные спонсорские каналы. Начальный продукт — **прокси-спонсорство, тариф 1 день — 300 ₽**, ручная модерация и ручное подтверждение размещения. В перспективе — автоматизация, метрики и масштабирование исключительно самостоятельного MTProxy Pushok.

## Правила разработки и выпуска

1. **Не переписывать без необходимости.** Использовать существующий FastAPI/PostgreSQL/API и уже готовые экраны v0.011.
2. **Начинать с безопасного ручного процесса.** Активация спонсорского тега не считается выполненной, пока оператор не подтвердил фактический результат.
3. **Готовые компоненты — после проверки.** Telemt — кандидат для прокси-движка; MTProxyMax и IGProxy — кандидаты для переиспользования идей и допустимых по лицензии компонентов. Для каждого: лицензия, активность, документация, безопасность, тесты совместимости.
4. **Никаких ложных цифр.** Различать подключённых к прокси, потенциальный охват, доказанные показы и переходы. Не обещать полноэкранное сообщение или гарантированные показы.
5. **Приватно до разрешения владельца.** GitHub/GitLab приватные; не публиковать кабинет, сервер, DNS и тестовый доступ автоматически.
6. **Полная автономность MTProxy Pushok.** Не добавлять связей с VPN, Remnawave или RemnaShop, не использовать их учётные данные, БД, сервисы и API. Пересмотр только по отдельному решению владельца.
7. **Безопасность по умолчанию.** Серверная RBAC-проверка, аудит действий, секреты вне Git, бэкапы перед миграцией, защищённая загрузка чеков, идемпотентность операций, ограничения частоты.
8. **Одна команда установки, но с понятным диалогом.** Русскоязычные варианты ответа, проверка среды, предварительный план, отмена, повторный запуск и проверки результата.

## Перспективное направление — Telegram Serverless (Beta)

**Статус на 2026-11-07:** у владельца бота `@mtproxy_pushok_bot` в BotFather отображается **«You're on the waitlist»**. Доступа к Serverless пока нет; сроки его получения неизвестны. Это **не блокирует** текущие этапы разработки.

**Решение:** сохранить существующий Telegram-бот на Python и FastAPI/PostgreSQL как основной вариант. После предоставления доступа отдельно оценить Telegram Serverless, который предлагает выполнение JavaScript-обработчиков на инфраструктуре Telegram. Не переносить автоматически всю бизнес-логику и не зависеть от бета-продукта.

Пошаговая оценка после получения доступа:

1. Проверить актуальные ограничения, цены, квоты, доступность внешних HTTP-запросов, обработку Bot API, секреты, журналы, хранение данных и правила платформы.
2. Сделать **маленький изолированный прототип**: `/start`, кнопка «Тарифы» и кнопка «Наш канал» → `https://t.me/pushok_proxy`; без платежей и доступа к боевой БД.
3. Сравнить с действующим Python-ботом: скорость отклика, надёжность, стоимость, диагностика, переносимость и удобство обновлений.
4. Если результат лучше — внедрить **гибридный режим**: Serverless обрабатывает Telegram-события, а наш приватный FastAPI остаётся источником истины для аккаунтов, кампаний, оплаты, модерации, аудита и MTProxy.
5. Сохранить переключение на собственный хостинг без миграции данных и проводить rollout только после тестов, контроля секретов и явного разрешения владельца.

**Критерий готовности:** прототип в тестовой среде проходит командные и негативные сценарии; отсутствуют дублирующиеся ответы/webhook-получатели; нет публичной утечки секретов; решение об использовании документировано. До этого — только пункт дорожной карты, не обещание доступности или интеграции.

## Фактический прогресс v0.017 — подтверждение канала и модерация (2026-11-08)

- Бот предлагает отдельную кнопку «Проверить канал и отправить на модерацию» после сохранения собственного черновика.
- Сервер **сам** проверяет Telegram Bot API: соответствует ли бот @mtproxy_pushok_bot, существует ли публичный канал, совпадает ли его @username, является ли бот администратором, является ли рекламодатель владельцем или администратором канала.
- Только после проверки статус заявки переводится из `draft` в `pending`. Числовой Telegram chat_id сохраняется в sponsor_channels, событие попадает в audit_events; повторное нажатие не создаёт второй записи.
- Чужие кампании не просматриваются через маршрут, а изменения в PostgreSQL условны по владельцу, каналу и статусу. Ошибки Telegram не записываются в журналы вместе с токеном.

## v0.029 — безопасная диагностика и тестовый маркер (2026-11-09)

`scripts/core_stage.py` предоставляет план без изменений, офлайн-проверку собранного ядра, пометку проверенного кандидата и возврат маркера к предыдущему состоянию. Прежде чем вызывать Rust CLI, инструмент проверяет checksum, полную лицензию и точные метаданные build-info; выполнение ограничено временем. Это **не запуск прокси** и **не rollback сервиса**. Веб-администратор видит осторожный read-only статус, права проверяются на сервере. Готовность live MTProxy, Telegram-клиентов и спонсорских размещений не выводится из успешной сборки. Следующий реальный этап — изолированный тест TCP/Telegram на отдельном staging-узле и контролируемое переключение только после разработки реального отката. Не задействовать VPN, Remnawave и RemnaShop.
