# Telegram-бот MTProxy Pushok — v0.021 (код, не развёрнут)

Бот: https://t.me/mtproxy_pushok_bot · канал: https://t.me/pushok_proxy.

## Что умеет эта версия

- `/start`, `/advertise`, `/campaigns`, `/tariffs`, `/channels`, `/help` и кнопки.
- `/campaigns` при **подключённом API** показывает до 10 последних **собственных** заявок: канал, тариф и статусы модерации, оплаты и размещения.
- Авторизация на чтение: Telegram передаёт достоверный `from.id` в обновлении; бот проверяет, что это личный чат того же пользователя. В API доступ к данным фильтруется по `users.telegram_user_id`.
- Только внутренний read-only маршрут `POST /api/v1/internal/bot/campaigns` с независимым секретом; он отсутствует в OpenAPI.
- Если секрет не настроен или API недоступен, бот сообщает об этом без раскрытия токенов, реквизитов и чужих данных.
- При старте бот сверяет `getMe` с `@mtproxy_pushok_bot` и отказывается запускать polling при активном webhook.

**Новый сценарий v0.016:** /advertise → ввести `@username` или `https://t.me/username` → подтвердить тариф «1 день — 300 ₽» → создать **черновик** в кабинете. Данные вводятся в личном чате с ботом. До подтверждения никакой записи о кампании нет. Заявка не оплачивается, не модерируется и не запускается автоматически. Для теста можно нажать «Отмена».

**Не реализовано:** отправка на модерацию из бота, редактирование заявки из бота, автоматическая оплата и включение спонсора, реальная статистика MTProxy. Бот ещё не развёрнут.

## Как настроить секреты безопасно

В **локальной** `.env`, которая не должна попадать в Git, нужен токен от BotFather и второй **независимый** секрет интеграции:

```bash
# Выполнить на своём сервере, НИКОГДА не присылать результат в чат.
openssl rand -hex 32
```

Полученные 64 символа в нижнем регистре вписываются как `BOT_INTERNAL_SECRET=<полученное_значение>`. Требуется строго 64 шестнадцатеричных символа, иначе внутреннее API будет недоступно. Установщик `setup.sh` генерирует секрет при **первой** настройке кабинета. При обновлении старой инсталляции `.env` сохраняется — добавьте переменную вручную, предварительно создав резервную копию.

Бот и API читают **одно и то же** значение из одной локальной `.env` в рамках Compose. Оно не равно `TELEGRAM_BOT_TOKEN` и не равно `SESSION_SIGNING_KEY`. Не размещайте токены в командах чата, issue, скриншотах, логе CI или документации.

## Новая миграция базы данных

В v0.016 появился файл `database/003_bot_draft_idempotency.sql`: необязательный UUID-ключ для защиты от повторной отправки Telegram-сообщений. На **новой** базе его выполняет PostgreSQL при инициализации контейнера; на **существующей** базе его нужно применить отдельно. Обновлённый `setup.sh` делает это при повторном запуске мастера, не удаляя данные, однако перед повторной установкой обязательно сделать резервную копию PostgreSQL и проверить конфигурацию.

Проверка миграции на локальном тестовом стенде:

```bash
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < database/003_bot_draft_idempotency.sql
```

Повторное применение должно быть безопасным; изменение выполняется только после осознанного запуска команды. Не использовать `docker compose down -v` для обновления: это удалит данные.

## Изоляция Docker

- `db`: только сеть `internal`.
- `api`: сети `internal` и `bot-api`.
- `bot`: сети `bot-api` (внутренний доступ только к API) и `bot-egress` (запросы Telegram).
- `BOT_INTERNAL_SECRET` нужен только боту и API; PostgreSQL не выдаёт учётные данные боту.
- Бот запускается как непривилегированный пользователь, read-only filesystem, без открытых TCP-портов.
- Публичный API никогда не принимает `telegram_user_id` без проверки отдельного секрета — этот маршрут не предназначен для вызовов из браузера.

## Критерии приёмки

1. Юнит-тесты включают проверку «чужой Telegram ID не получает чужие кампании» и проверку приватного создания черновика с фиксированным тарифом.
2. API отвергает отсутствующий/неверный/шаблонный секрет **до** чтения БД.
3. После тестового запуска бот показывает данные реальных кампаний владельца и не возвращает чужие.
4. Телеграм-бот правильно сообщает о недоступности API и не показывает секреты.
5. Нет внешних API-портов или изменений VPS/магазина без разрешения.

6. Повторное нажатие «Создать черновик» после сетевой ошибки не создаёт вторую кампанию благодаря `bot_request_key` в PostgreSQL.

**Важно:** состояние короткого двухшагового диалога живёт в памяти одного бота не дольше 10 минут. При перезапуске диалог потребуется начать заново, но уже сохранённая кампания останется в БД. Публичный канал нужно предварительно проверить — корректный username сам по себе не доказывает права рекламодателя на канал.

**Проверено:** GitHub Actions (PR #1): 64 теста с реальной тестовой PostgreSQL и Compose smoke-test — успешно. **Остаётся:** запуск на VPS и проверка реальных Telegram-сообщений, без включения платежей и спонсора.

## Подтверждение канала через Telegram Bot API — v0.017

После сохранения черновика нажмите кнопку **«🔍 Проверить канал и отправить на модерацию»**. Для успешной проверки:

1. Указанный канал должен быть **публичным**, с тем же @username, что в заявке.
2. Добавьте `@mtproxy_pushok_bot` администратором этого канала. Не нужно выдавать ему права на публикацию или удаление сообщений, если Telegram позволяет назначить более ограниченные права. **Не передавайте токен бота рекламодателю.**
3. Телеграм-аккаунт рекламодателя, который общается с ботом, должен быть владельцем или администратором того же канала.
4. В личном чате нажмите кнопку проверки ещё раз. Сервер вызовет официальные `getMe`, `getChat` и `getChatMember`; одного публичного @username для доказательства недостаточно.

Когда права подтверждены, заявка переходит в статус **«На модерации»** (`pending`). В журнале аудита появляется `campaign_submitted_from_bot`. Повторное нажатие безопасно: уже ожидающая модерации заявка возвращает тот же статус без создания нового события.

**Важно:** это проверка административного доступа, не юридических прав на канал. Не происходит списания денег, публикации рекламы, включения спонсорского тега или запуска прокси. Оператор по-прежнему отдельно принимает решение по модерации.

Если Telegram временно недоступен, права не подтверждены либо бот не администратор, **черновик остаётся черновиком**. Статус не меняется. В логах не должны выводиться URL ошибок, содержащие Telegram-токен.

Секретный маршрут `POST /api/v1/internal/bot/campaign-drafts/submit` принимает UUID кампании и ID пользователя только от доверенного бота (`BOT_INTERNAL_SECRET`). Пользователь проверяется и на стороне бота, и посредством JOIN с владельцем заявки в PostgreSQL. Статус обновляется условным SQL `UPDATE` с аудитом в одной транзакции.

## Модерация и уведомления — v0.018

Команда `/moderation` в **личном чате** с `@mtproxy_pushok_bot` доступна только пользователям, которые в PostgreSQL записаны как `operator` или `admin`. Роль определяется по Telegram ID отправителя. Один лишь username не предоставляет прав.

Команда открывает 5 самых ранних заявок `pending` и добровольно подписывает оператора на уведомления. Кнопки:

- **✅ Одобрить** — отдельный шаг подтверждения; результат `approved` и `awaiting_payment`.
- **❌ Отклонить** — бот ждёт текстовую причину от 3 до 2000 символов; результат `rejected`.
- **✏️ Исправить** — бот ждёт комментарий с требованиями; результат `changes_requested`.

Все решения пишутся в `audit_events` в одной транзакции с изменением `campaigns`. Повторное нажатие на уже обработанную заявку вернёт отказ, не создавая дублирующих событий. Причины видны в кабинете рекламодателя.

`/moderation_off` отключает уведомления и не меняет права оператора. При потере роли operator/admin прекращается и доступ к очереди, и доставка уведомлений. **Telegram-бот не может первым написать пользователю**, который не открыл с ним чат; поэтому сначала оператор должен сам открыть диалог и вызвать команду. Рассылка ограничена пятью подписчиками за событие, выполняется как `best effort`: после сбоя сети возможно отсутствие уведомления, но кампания остаётся в очереди PostgreSQL. Надёжная транзакционная outbox-рассылка — будущий этап.

На новых PostgreSQL-томах `database/004_operator_bot_subscriptions.sql` применяется при создании базы. На старых примените миграцию **после резервного копирования**:

```bash
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < database/004_operator_bot_subscriptions.sql
```

Обновлённый мастер `setup.sh` также применяет её к существующей базе. Никакие действующие данные и платежи не удаляются. Не выполняйте `docker compose down -v` при обновлении.

Проверки: `python3 -m unittest tests.test_bot_operator tests.test_bot_operator_api tests.test_postgres -v` с отдельной PostgreSQL для последнего набора. Бот и сервисы **не развёрнуты на пользовательском VPS** в рамках этой разработки.

## v0.019 — повторяемые уведомления с PostgreSQL outbox

После успешного перевода собственного черновика в `pending` в **той же
транзакции** появляются записи в `bot_operator_notice_outbox` для максимум
пяти подписанных операторов с действующими ролями `admin/operator`.
Отправка выполняется только ботом, без доступных публике HTTP-маршрутов.

Внутренний маршрут `operators/outbox/claim` выбирает до пяти сообщений,
блокирует строки на время транзакции (`FOR UPDATE SKIP LOCKED`), отмечает
время попытки и предотвращает следующий claim на протяжении минимум 2 минут.
После успешного `sendMessage` бот вызывает `operators/outbox/ack`, который
сохраняет `delivered_at`. Если Telegram отказал или бот перезапустился,
неподтверждённые сообщения остаются в БД и будут повторены. После
`sendMessage` и до ACK сообщение могло быть получено пользователем:
**дубликаты возможны**.

Команда `/moderation_off` отключает подписку; смена роли также запрещает
дальнейшую выдачу отложенных уведомлений. Нельзя обещать, что Telegram
получил сообщение, только по факту формирования outbox.

Миграция (на старой установке только после резервной копии):

```bash
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < database/005_operator_notice_outbox.sql
```

Для новых БД миграция выполняется при инициализации Docker PostgreSQL.
`setup.sh` применяет миграцию и при обновлении существующего кабинета.
**Не использовать `docker compose down -v` для обновления**: том с БД
будет удалён.

Проверки `tests/test_bot_outbox_api.py` и
`test_operator_outbox_survives_retries_and_role_revocation` в
`tests/test_postgres.py` проверяют проверку секрета, отозванную роль,
таймауты попыток, ACK и отсутствие второй записи аудита.
Реальный запуск на VPS остаётся отдельным этапом.


**Итог CI v0.019:** [GitHub Actions run](https://github.com/mrkoster1988/mtproxy-pushok/actions/runs/42463859043): 120 тестов и Docker Compose smoke-test — успешно. Это не заменяет реальную проверку Telegram API и VPS.


## v0.020 — уведомления рекламодателю о решении модератора

Запись о решении создаётся **в той же транзакции PostgreSQL**, что и смена статуса заявки. Это работает и для веб-модерации, и для модерации через бота. Бот периодически отправляет уведомления владельцу заявки: одобрено (ожидание оплаты), отклонено с причиной или запрошены исправления. Денег он не списывает и спонсора не активирует.

Обновление существующей базы (только после резервной копии):

```bash
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < database/006_advertiser_notice_outbox.sql
```

На чистом томе файлы миграций PostgreSQL выполняются автоматически в порядке имён; установщик дополнительно применяет `006` к существующему тому. Повторная миграция безопасна: триггер пересоздаётся, старые события не удаляются.

Сообщение нельзя гарантировать пользователю, который ещё не написал боту или заблокировал его. При Telegram 403 запись помечается как недоставляемая. При временном сетевом сбое письмо остаётся в очереди и повторяется с задержкой (от 2 до 60 минут). После `sendMessage`, но до ACK возможна дублирующая доставка — ровно один раз не гарантируется.

**Безопасность:** маршруты уведомлений доступны только с `BOT_INTERNAL_SECRET`, не включаются в OpenAPI; получатель выводится из владельца кампании на стороне БД, а не присылается ботом. Комментарий модератора перед отправкой очищается от управляющих символов и ограничивается по длине; Telegram Markdown/HTML отключены.

Проверки кода: `python -m unittest tests.test_advertiser_notices_api tests.test_advertiser_notices_bot tests.test_postgres -v` с отдельной тестовой PostgreSQL. Проверка работоспособности на VPS требует отдельного запуска, пользовательский сервер в ходе разработки не менялся.

## Диагностика отправок и безопасный предпусковой тест — v0.021

В личном чате с ботом `@mtproxy_pushok_bot` администратор кабинета может отправить `/delivery` (при желании добавить команду в BotFather). **Нужна именно роль `admin` в PostgreSQL**, username Telegram или роль `operator` недостаточны. Бот покажет количество ожидающих, обрабатываемых, отправленных и постоянно недоставленных уведомлений. Отдельно выводятся последние 8 недоставленных уведомлений рекламодателей с числом попыток, но **без телефона, Telegram ID получателя, токенов и текста модерации**.

Кнопка «Повторить» ускоряет ещё не доставленную отложенную попытку, только если срок текущего lease истёк. Из статуса «постоянный отказ» (Telegram 403) вручную через бота сообщение не переводится. Каждая ручная операция фиксируется в `audit_events`; невозможно «повторить» уже отправленное сообщение. Реальное `sendMessage` делает существующий обработчик outbox.

При подготовке выделенного staging-хоста запустите из каталога репозитория **только чтение и валидацию**:

```bash
bash -n setup.sh
bash -n scripts/staging_preflight.sh
bash scripts/staging_preflight.sh
```

Последняя команда проверяет существующий приватный `.env`, `TELEGRAM_BOT_TOKEN`, независимый `BOT_INTERNAL_SECRET`, `SESSION_SIGNING_KEY` и валидность `docker compose --profile bot config --quiet`; **не печатает токены, не меняет конфигурацию, не запускает БД, API или бота**. Запускать её следует только на отдельном staging после подготовки `.env`; результаты проверки можно сообщить без значений секретов.

В этой итерации нет дополнительных миграций: диагностика использует уже созданные таблицы outbox миграций `005` и `006`. Для старых инсталляций проверяйте, что эти миграции были применены, перед включением бота. Перед любым реальным обновлением обязательна резервная копия PostgreSQL.

Проверки разработчика:

```bash
python -m unittest tests.test_bot_delivery_admin_api tests.test_bot_delivery_inbox tests.test_staging_preflight -v
```

Проверку на реальном Telegram и пользовательском VPS не проводили; зелёный CI сам по себе не означает, что пользователи получают уведомления.
