# Telegram-бот MTProxy Pushok — v0.016 (код, не развёрнут)

Бот: https://t.me/mtproxy_pushok_bot · канал: https://t.me/pushok_proxy.

## Что умеет эта версия

- `/start`, `/advertise`, `/campaigns`, `/tariffs`, `/channels`, `/help` и кнопки.
- `/campaigns` при **подключённом API** показывает до 10 последних **собственных** заявок: канал, тариф и статусы модерации, оплаты и размещения.
- Авторизация на чтение: Telegram передаёт достоверный `from.id` в обновлении; бот проверяет, что это личный чат того же пользователя. В API доступ к данным фильтруется по `users.telegram_user_id`.
- Только внутренний read-only маршрут `POST /api/v1/internal/bot/campaigns` с независимым секретом; он отсутствует в OpenAPI.
- Если секрет не настроен или API недоступен, бот сообщает об этом без раскрытия токенов, реквизитов и чужих данных.
- При старте бот сверяет `getMe` с `@mtproxy_pushok_bot` и отказывается запускать polling при активном webhook.

**Новый сценарий v0.016:** /advertise → ввести `@username` или `https://t.me/username` → подтвердить тариф «1 день — 300 ₽» → создать **черновик** в кабинете. Данные вводятся в личном чате с ботом. До подтверждения никакой записи о кампании нет. Заявка не оплачивается, не модерируется и не запускается автоматически. Для теста можно нажать «Отмена».

**Не реализовано:** отправка на модерацию из бота, редактирование заявки из бота, автоматическая оплата и включение спонсора, реальная статистика MTProxy. Бот ещё не развёрнут.

## Как настроить секреты безопасно

В **локальной** `.env`, которая не должна попадать в Git, нужен токен от BotFather и второй **независимый** секрет интеграции:

```bash
# Выполнить на своём сервере, НИКОГДА не присылать результат в чат.
openssl rand -hex 32
```

Полученные 64 символа в нижнем регистре вписываются как `BOT_INTERNAL_SECRET=<полученное_значение>`. Требуется строго 64 шестнадцатеричных символа, иначе внутреннее API будет недоступно. Установщик `setup.sh` генерирует секрет при **первой** настройке кабинета. При обновлении старой инсталляции `.env` сохраняется — добавьте переменную вручную, предварительно создав резервную копию.

Бот и API читают **одно и то же** значение из одной локальной `.env` в рамках Compose. Оно не равно `TELEGRAM_BOT_TOKEN` и не равно `SESSION_SIGNING_KEY`. Не размещайте токены в командах чата, issue, скриншотах, логе CI или документации.

## Новая миграция базы данных

В v0.016 появился файл `database/003_bot_draft_idempotency.sql`: необязательный UUID-ключ для защиты от повторной отправки Telegram-сообщений. На **новой** базе его выполняет PostgreSQL при инициализации контейнера; на **существующей** базе его нужно применить отдельно. Обновлённый `setup.sh` делает это при повторном запуске мастера, не удаляя данные, однако перед повторной установкой обязательно сделать резервную копию PostgreSQL и проверить конфигурацию.

Проверка миграции на локальном тестовом стенде:

```bash
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < database/003_bot_draft_idempotency.sql
```

Повторное применение должно быть безопасным; изменение выполняется только после осознанного запуска команды. Не использовать `docker compose down -v` для обновления: это удалит данные.

## Изоляция Docker

- `db`: только сеть `internal`.
- `api`: сети `internal` и `bot-api`.
- `bot`: сети `bot-api` (внутренний доступ только к API) и `bot-egress` (запросы Telegram).
- `BOT_INTERNAL_SECRET` нужен только боту и API; PostgreSQL не выдаёт учётные данные боту.
- Бот запускается как непривилегированный пользователь, read-only filesystem, без открытых TCP-портов.
- Публичный API никогда не принимает `telegram_user_id` без проверки отдельного секрета — этот маршрут не предназначен для вызовов из браузера.

## Тестовая проверка и запуск по решению владельца

```bash
python3 -m unittest tests.test_bot tests.test_bot_api tests.test_bot_wizard tests.test_bot_drafts_api -v
docker compose --profile bot config --quiet
```

**Только после успешных проверок и на выбранном тестовом сервере:**

```bash
docker compose --profile bot up -d --build bot
docker compose --profile bot ps bot
docker compose --profile bot logs --tail=50 bot
```

API и PostgreSQL должны быть предварительно запущены из того же Compose-проекта для просмотра кампаний. При запуске только контейнера бота кнопки `/start` и `/tariffs` работают, а `/campaigns` покажет сообщение о временной недоступности данных. Контейнер не стартует при обычном `docker compose up` без профиля.

Остановить бот: `docker compose --profile bot stop bot`. Не запускайте два polling-процесса на одном токене, не удаляйте существующий webhook автоматически.

## Критерии приёмки

1. Юнит-тесты включают проверку «чужой Telegram ID не получает чужие кампании» и проверку приватного создания черновика с фиксированным тарифом.
2. API отвергает отсутствующий/неверный/шаблонный секрет **до** чтения БД.
3. После тестового запуска бот показывает данные реальных кампаний владельца и не возвращает чужие.
4. Телеграм-бот правильно сообщает о недоступности API и не показывает секреты.
5. Нет внешних API-портов или изменений VPS/магазина без разрешения.

6. Повторное нажатие «Создать черновик» после сетевой ошибки не создаёт вторую кампанию благодаря `bot_request_key` в PostgreSQL.

**Важно:** состояние короткого двухшагового диалога живёт в памяти одного бота не дольше 10 минут. При перезапуске диалог потребуется начать заново, но уже сохранённая кампания останется в БД. Публичный канал нужно предварительно проверить — корректный username сам по себе не доказывает права рекламодателя на канал.
