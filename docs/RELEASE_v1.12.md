# MTProxy Pushok v1.12

Исправлено обновление с v1.09, которое останавливалось на этапе базы данных при наличии системных событий о завершении кампаний.

- Старый установщик повторно выполнял 002–033. Ограничение из 030 запрещало уже допустимые с 031 записи `placement_completed_by_agent`. Повторное применение теперь сохраняет эти записи и разрешённые события аудита.
- Установщик ведёт журнал `pushok_schema_migrations`: применённые файлы не запускаются снова; изменение их содержимого обнаруживается по SHA-256. На старой базе без журнала один раз выполняется совместимый проход 002+.
- Миграции и журнал фиксируются одной транзакцией под общей блокировкой. При ошибке SQL весь текущий проход отменяется, ранее существовавшие данные остаются. Автоматического восстановления базы из старой копии нет.
- В журнале службы при ошибке видны файл миграции и SQLSTATE, без значений строк и секретов. Кабинет показывает текущий этап работы обновляющей службы.

## Установка после неудачной попытки

В кабинете: «Профиль → Версия и обновления → Проверить → Установить v1.12». Дождитесь завершения текущей попытки, если кнопка занята. Версии v1.10 и v1.11 отдельно устанавливать не нужно. После успешного обновления поле «Установлено» должно показывать v1.12.

Если кабинет долго остаётся недоступен, на VPS проверьте `systemctl status mtproxy-pushok-updater.service --no-pager` и `journalctl -u mtproxy-pushok-updater.service -n 80 --no-pager`. Не удаляйте том базы и не запускайте повторную первичную установку.

## Проверки

Регрессионный тест на отдельной PostgreSQL создаёт схему v1.09 с системным завершением, воспроизводит отказ старого ограничения, выполняет обновление и повторный запуск, проверяет сохранение истории, новые таблицы, отказ при изменении применённого файла и транзакционный откат ошибочной новой миграции. Проверка CI не означает, что обновление уже установлено на пользовательском VPS.
